## Contested and resolved: does a "finished playing" signal reach the brain in production?

This is the one direct disagreement, and it's the master prompt's headline example of a case that needs resolving "using code, tests, experiments, architectural reasoning — not authority."

**Codex's claim**: "A completed-playback signal does reach BrainAgent in the production wiring" — transport queues a completion marker behind PCM and publishes `AudioPlaybackProgress(completed=True)`; BrainAgent subscribes and consumes it (`transport_agent.py:407-438,443-465,522-562`; `brain_agent.py:283-288,1150-1177`). Caveated only as "not a hard guarantee" (spawned, not awaited; can be dropped on a full queue).

**My claim** (this session, before reading C1): the signal never fires in production because `is_done` is only set from a dict-shaped NATS payload, and the only producer on `audio.stream` sends raw bytes.

**Resolution**: both of us read `transport_agent.py`'s consumer side correctly — the `FIX-CLD-02` completion-marker machinery Codex cites is real, well-built, and does exactly what its comments say *if it ever receives `is_done=True`*. The disagreement is entirely about the **producer** side, which Codex's citations never touch. I traced every possible producer of the `audio.stream` topic exhaustively this session:
- Python: `grep -rn "audio.stream\|AUDIO_STREAM" backend/app` finds exactly three files — `config.py` (lists it as a binary subject), `contracts.py` (defines the constant), `transport_agent.py` (subscribes only). No Python code anywhere publishes to this topic.
- Rust: the only publisher is `voice-agent`'s `publish_pcm` (`crates/voice-agent/src/main.rs:1715,1754`), which always sends `Bytes::from(pcm)` — raw bytes, never a JSON/dict payload with a `done` key. Confirmed with `grep -n '"done"'` across both the Rust voice-agent and the Python agents — the only `"done"` dict key check anywhere is the consumer-side `transport_agent.py:337`, with nothing constructing that shape to send.
- `transport_agent.py` itself subscribes to exactly three subjects (`audio.stream`, `audio.stop`, `audio.playback.visemes`) — not `chat.output` — so there is no alternate path by which a `chat.output.done` event could reach `_on_nats_audio` and set `is_done`.

**Verdict**: `is_done` can never be `True` on the real production path. The completion marker at `transport_agent.py:407-438` is unreachable dead code today — built (per its own `FIX-CLD-02` comment) specifically to solve this gap, but never connected to a producer that emits the shape it's waiting for. This is not a new discovery of the underlying gap (ADR-003 already documents "no reliable finished-playing event" as known and unfixed) — it's a correction to Codex's specific claim that the fix already lands in production, and a sharper diagnosis for workstream W4: the fix isn't "build the lifecycle contract," it's "connect voice-agent (or transport, once it can observe LiveKit playout directly) to the completion-marker machinery that already exists but has no producer." That changes W4's scope from a from-scratch build to a producer-side wiring job plus the STARTED/INTERRUPTED/FAILED states the marker machinery doesn't cover yet.

**Why the disagreement happened**: Codex's audit is careful and its consumer-side citations are all accurate — it just didn't run the negative check (who actually produces this payload) before asserting the positive claim. That asymmetry — verifying that a mechanism *would* work without verifying that anything *invokes* it — is exactly the failure mode Objective 9 asks this cycle to hunt for across the rest of the codebase, and it's worth remembering as a standing check for every workstream's own adversarial review: prove the producer exists, not just that the consumer is correct.

## C0 (infrastructure): findings folded into `04-local-infrastructure.md` / `findings.md`

C0 found several things my Phase 0 pass didn't check, in the same read-only, code-first style, all with file:line:

- **High**: LiveKit runs with `network_mode: host` (`docker-compose.infra.yml:100`), which bypasses the loopback-only port policy the rest of the compose file enforces — LiveKit's own ports (7880/7881/50000-51000 UDP, `livekit.yaml:1-2`) bind to all addresses regardless. `mesh-integrity.yml`'s loopback check only scans explicit port mappings, so it passes without ever looking at this. This is the same class of gap the P0-2 audit comment says was already fixed once (2026-08-22) — it wasn't fully fixed.
- **Medium**: Qdrant's own healthcheck (`./qdrant --version || exit 0`) can never report failure — it always exits 0. Ours showed "healthy" in Phase 0; that status is not trustworthy on its own.
- **Medium**: NATS runs with no auth by default; `nats-accounts.conf` documents an opt-in path Compose never enables.
- **Medium**: Postgres port disagreement across `.env.example`/`env_wizard.py` (5432) vs. `docker-compose.infra.yml` (5433) vs. `check_prereqs.py` (checks 5432). Directly relevant: our own tunnel setup used 5433 correctly because I read the compose file directly, but any script trusting `.env.example`'s port would silently connect to nothing.
- **Medium**: the GPU experiment README's build instructions omit installing `maturin` and don't match the actual CI invocation (`ci.yml:117`) — this matches my plan's Phase 4 instruction to audit the GPU package *before* running it, now with a concrete fix (copy the CI invocation, add the maturin install step) rather than a general "check it works."
- **Medium**: `mesh-integrity.yml`'s env-completeness check is warning-only, not a failing gate.

None of these contradict anything in `04-local-infrastructure.md`; they extend it. Full list preserved in the archived Codex output; the ones with direct action items are copied into `findings.md` as F-002 through F-004 (see that file) rather than duplicated here.
