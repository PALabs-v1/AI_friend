# P8: scale testing

Owns (see `COVERAGE.md`): DR-024 (latency budgets), C1-3's live-store
extension to scale. Feeds W6 (ADR-004 storage roles), W7 (growth), W8
(abstention floor on real embeddings).

## Question

At 1k, 10k, 100k, 500k and 1M memories (5M if disk and time allow), with
real `nomic-embed-text` embeddings of realistic lifesim memory text, how do
production's retrieval backends behave, and does the brain stay inside
DR-024's budgets? The budgets are reflex < 50 ms, interactive
time-to-first-audio 300-500 ms, and background never delaying foreground.

## Deliverables

1. `backend/tools/scale/` (new package, own README, own tests):
   - **corpus**: memory texts from lifesim (`evals/lifesim`, dev seeds only,
     many personas and long horizons), deduplicated, with provenance per row
     (seed, archetype, turn). Deterministic for a given size and seed list.
   - **embed once**: embeddings computed once with the production embedder
     path (`nomic-embed-text` via Ollama, production's prefix policy: none,
     per M-12), cached as `.npy` + manifest (model digest, count, sha256) on
     a configurable data dir. Every backend reads the same cache. Resumable,
     batch-parallel, with progress/rate/ETA to a progress log.
   - **load** into each backend through production code paths where one
     exists (`MemoryStore.add_memory` or its bulk equivalent; say which and
     why):
     - SQLite index (`sqlite_vector_index.py`, `MEMORY_SQLITE_SCAN_LIMIT`
       behaviour included: measure what happens past 5000)
     - Postgres + pgvector HNSW
     - Qdrant at the repo's pinned image (v1.9.0) and at the latest stable
       image
     - Neo4j entity graph with lifesim's real edge density
   - **measure** per backend and size:
     - retrieval latency P50/P95/P99 through `MemoryStore.search_memories`
       (the path a turn takes), plus the raw backend query time
     - index build time
     - RSS, DB and disk size
     - CPU; GPU for embedding
     - graph traversal cost (1-hop and 2-hop from a random entity)
     - a consolidation/decay pass time
     - foreground turn latency while a background consolidation runs (DR-024
       starvation: background must never delay foreground)
     - recall sanity: hit@k on lifesim probes whose answers are in the
       corpus, so a fast-but-wrong backend is visible
   - **report**: JSON per run plus a markdown table; every number carries
     git sha, image tags, model digest and hardware.
2. Tests (Mac, no network): the whole pipeline at N=200 with a deterministic
   stub embedder and SQLite only, covering determinism, resumability, cache
   manifest verification (refuses a mismatched cache), and report shape.
   Backends that need a live service get an integration test that skips
   cleanly when the service is absent.
3. `docs/brain-research-v3/11-scale.md` written from the real run (by the
   reviewer after running on home-gpu), and `results/scale/` raw JSON (small
   text only).

## Where it runs

home-gpu, data under `/data` only (never `/`), compose project `aifv3`,
one backend at a time (16 GB RAM), Docker memory limits set. The builder's
sandbox cannot reach home-gpu: build and test locally at small N. The
reviewer runs the real sizes.

## Acceptance (mechanical)

- Every size x backend cell present in the report, or explicitly marked
  not-run with the reason (for example, 5M skipped for disk, with the
  number).
- For each backend, the size at which `search_memories` P95 exceeds the
  interactive budget's retrieval share, named or shown not to happen up to
  1M.
- Foreground latency under background load compared against the no-load
  number at the same size.
- Recall sanity reported beside the latency numbers.
- Rust is used only if a profile shows a hotspot the budget cannot absorb.
