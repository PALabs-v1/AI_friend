# W4: voice playback lifecycle contract

Owns (see `COVERAGE.md`): V-2, F-002, DR-029, SW-5 (Rust contracts missing
topic constants), G-4 (which TTS the live mesh run uses). Supplies the
lifecycle W5 builds on (F-013, DR-026/027/028/030).

## Problem

The brain never learns that a reply finished playing. `transport_agent.py`
has correct completion-marker machinery (`FIX-CLD-02`, ~407-438) keyed on a
dict payload with `done=True`, but the only producer of `audio.stream`
(`crates/voice-agent/src/main.rs` `publish_pcm`) always publishes raw bytes
(F-002). So `OutcomeRecord` COMPLETED never happens: BrainBench barge-in
measured 0 COMPLETED outcomes across 350 scenarios (F-013). Separately,
self-correction publishes an unscoped confirmed `audio.stop` that cancels its
own retry (V-2). DR-029 says a started self-correction always finishes.

## Decisions to honour

- DR-029: self-correction always finishes; `AudioStop` must tell "stop, and
  let a self-correction proceed" apart from "stop everything".
- DR-027: word-level heard-text granularity (unchanged here; W5 applies it).
- DR-024: interactive time-to-first-audio 300-500 ms. W4 must not add latency
  to the first audio frame; measure it.

## Deliverables

1. **Contract** `audio.playback.lifecycle` (new topic) in
   `backend/app/contracts.py` and `backend/crates/contracts/src/lib.rs`, with
   fixture parity in `tests/test_rust_contract_fixtures.py`:
   - states STARTED -> PLAYING (progress) -> exactly one of
     {COMPLETED, INTERRUPTED, FAILED}
   - keyed by `utterance_id` + `turn_id`
   - monotonic `seq` per utterance
   - terminal states idempotent: a duplicate terminal is ignored; a second,
     different terminal is a protocol error, logged and counted, and never
     applied
   - `words_played` / heard offset carried on PLAYING and on the terminal
     event, so W5 can truncate history to what was heard
   Add the topic constant to the Rust crate, and every other `Topics` constant
   the Rust crate lacks today (SW-5), with a parity test that fails when the
   two sides diverge.
2. **Producer.** Transport owns actual playout, so transport emits the
   lifecycle: STARTED on first frame written to the LiveKit source, PLAYING
   progress, COMPLETED when the last frame of the utterance has been
   *played out*, not when it was received. Transport needs to know an
   utterance's stream has ended: add an end-of-stream trailer on
   `audio.stream` from voice-agent (a typed trailer the transport recognises;
   the raw-bytes frames stay unchanged), and keep the existing FIX-CLD-02
   FIFO-marker approach for "played, not buffered". INTERRUPTED on an applied
   stop, FAILED on source or encoder failure. Delete or wire every piece of
   the old completion path so exactly one mechanism exists.
3. **`AudioStop.flush`** (V-2, DR-029) on both sides: the self-correction path
   sends a scoped stop that flushes the wrong audio without aborting the
   turn's retry. The brain's `_on_audio_stop` must not cancel the generation
   that is running the retry. Voice-agent (`main.rs` ~840) must not abort the
   rest of the turn on a flush-stop.
4. **Consumer.** `brain_agent.py` consumes the lifecycle, and the
   `OutcomeRecord` COMPLETED path becomes live. Exactly one terminal outcome
   per reply.
5. **Property tests on the state machine in both languages**: Rust `proptest`
   and Python `hypothesis`. Invariants:
   - one terminal state per utterance
   - `seq` strictly increasing; out-of-order and duplicate delivery are
     handled
   - no transition out of a terminal state
   - heard offset never exceeds words streamed
6. **Live mesh check** script
   `backend/scripts/voice_lifecycle_mesh_check.py`: drives voice-agent,
   transport and brain over a real NATS, and asserts STARTED -> COMPLETED and
   STARTED -> INTERRUPTED end to end. It also asserts that a self-correction
   (flush stop) finishes its retry. State which TTS it uses (G-4: GPT-SoVITS
   weights are empty; a stub or alternative TTS is fine if named and
   justified). The builder writes it and runs whatever parts its sandbox
   allows; the reviewer runs it for real.

## Acceptance (mechanical)

- BrainBench barge-in suite:
  - `completed_outcome_count` > 0 on replies that play in full, and
    `replies_unresolved_without_completion` -> 0.
  - Every ADR-003 claimed invariant stays at 0 violations.
  - Report the per-family table before and after (`invariant_violation_rates`,
    `outcome_accounting`).
  - The barge-in suite may need its fake transport updated to emit the new
    lifecycle; any suite change must be justified in the report and must not
    weaken a check.
- `tests/test_brainbench_gates.py` passes. Barge-in bands may only move in the
  better direction.
- Rust: `cargo test --workspace` green. Python: every touched module's tests
  plus the contract parity tests.
- `scripts/barge_in_mutations.py` re-run: kill count not lower than 33/38.
- Time-to-first-audio unchanged within noise (measured before/after on the
  mesh check).

## Out of scope

W5's history truncation on ordinary barge-in (DR-028), serial `chat.input`
(V-3), the proactive grace window (DR-030). W4 provides the signals; W5
changes what the brain does with them.
