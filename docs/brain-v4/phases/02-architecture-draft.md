# Phase 02: Brain V4 architecture draft

Status: architecture proposal for Phase 03 cold critique. No implementation is authorized by this document. Phase 04 turns accepted parts into slices; Aniket approves the slices before code work (D-009, D-015, `PROJECT_STATE.md`).

## 1. Purpose and non-goals

V4 asks whether an external, persistent state system can make later choices and replies depend on a mind's history in a way that people experience as a coherent someone. The target is a mind without a physical body: language, memory, affect, drives, voice, vision, agency, and continuity. It is not a body simulation or a claim that software has subjective experience (`README.md`; D-009, D-015).

The architecture is a typed state ledger with processing layers and paths. Each row names its timescale, writers, readers, intervention handle, and behavioral measure. A row is not called causally closed because code mentions it in a prompt. Under D-020, closure requires a pre-registered clamp, swap, or ablation to change the named behavior through the channel claimed. D-015 keeps the three layer names and treats “how close” as a profile of measures, not one score.

No claim is made that the system is conscious, has feelings, has a soul, or has human experience. Whether an artificial system has subjective experience is outside the test and remains UNKNOWABLE (`README.md`; D-009; `05-phase01-comparison.md`, sections 3 and 8). The measurable claim, if evidence supports it, is narrower: persistent, loop-generated state changes later behavior and helps raters experience more continuity or agency.

D-004 requires the mind to say it is an AI when asked and forbids claims of a human past or body. D-018 interprets this as self-knowledge held in the mind and expressed in its own voice, not stock assistant disclaimers. The mind can speak naturally and still answer a sincere “are you human?” probe honestly. D-019 permits user-authored backstory only as labeled background, never as lived memory. The mechanism and its unresolved interpretation check are in section 4.

This draft keeps V3 frozen (D-010). It proposes no edits to `docs/brain-research-v3/` and no changes on branch `brain-v3`. The V3 re-check is evidence for this design only; its corrections stay in `research/v3-recheck.md` unless Aniket separately authorizes V3 edits (D-030).

Partnership is a capability in its own right (D-007). Fictional examples such as Vision Quest and PRAGMATA remain design prompts, not evidence about minds (D-014; `RISK_REGISTER.md`, R-07).

## 2. State ledger

Statuses use the requested labels. **Closed** requires the D-020 intervention gate to pass; none has passed in the current code. **Self-loop** means state feeds its own update. **Open-write** means a value is read but its intended writer is missing, disabled or blocked. **Open-read** means a value is written but its claimed behavioral read is absent or unproven. **No reader** means a value is written and nothing reads it. **Decorative** means no live cognitive path. **By design** means the absence of a writer is intended by the persona tier system. Derived values are not stored rows: arousal adds energy, fatigue and adrenaline terms (`backend/app/state/agent_state.py:313-339`), trust is the mean of its three dimensions, and cortisol has a tonic part from mood and fatigue, so a clamp is defined on the stored component and the report names it. A code path alone does not satisfy D-020. Timescale labels are design placements, not measured durations.

## 3. Layers and paths

D-031 fixes the mapping: reactive is the reflex plus interactive paths; deliberative is the deliberative path; reflective is the background path. Identity is not a fourth processing layer. It is the slow ledger rows and constraint set used across the three. This follows D-015's layers-within-loops framing while giving every path ledger inputs and outputs.

| Layer | Job | Ledger reads | Ledger writes | Latency budget | Measure |
|---|---|---|---|---|---|

## 4. Identity and in-character AI self-knowledge

### Identity rows and constraints

Identity consists of the slow rows in section 2, with four explicit records: (1) user-authored immutable persona core; (2) adaptive traits and relationship fields; (3) baseline PAD set-point and other constitutional temperament values, fixed by the tier system unless Aniket decides otherwise (section 11); (4) self-description including “I am an AI,” model identity, and provenance. The authored backstory is a separate labeled background record, not first-person lived memory (D-005, D-019). Every identity write records source, date, corroboration count, prior value, and new value so that a test can restore or clamp the row.

D-025 governs adaptive-field writes: commit automatically only after N corroborating reflections on separate days. The exact N and thresholds come from a lifesim sweep; this draft does not invent them. The immutable core cannot drift. Users get no reset. A developer snapshot and restore is allowed only on an offline test copy, which is deleted after testing (D-005, D-025, D-027, D-029). The repo still ships a reset path, `backend/scripts/reset_persona.py` with `backend/app/persona/reset.py`, that deletes the persona row and seeded memories, against D-025 and DR-033 ("No reset mechanism, by design"); it is limited to developer offline copies or removed (section 9).

One model is pinned to one mind for its life (D-026). Different minds may start on different model tiers (D-003, D-024), but a live mind does not change models or receive a model-swap notice. For a long-lived mind the model has self-hosted local weights; the pin includes at least model name, version, weights hash and the embedding model (D-029; `RISK_REGISTER.md`, R-12). Backup and restore may move the same mind and same model to another machine. Only one live copy per lineage is permitted; offline intervention copies never go live and are removed after the experiment (D-027, D-029). Current local and frontier models are test vehicles, not the final model home (D-032). The future from-scratch model track is out of this architecture build; its narrow-role pilot, data and compute gates remain as stated in D-033 to D-035.

### AI self-knowledge mechanism

Store a typed, immutable self-description with provenance: AI status, lack of a human body or human lived past, the persona's authored background label, and the pinned model identity. Put the concise self-description in the persona context builder as a fact about the mind. Keep the authored story separately marked as background. The authored background is relabeled in the same change: row 25 shows `seed_biography` storing it as first-person episodes and the prompt presenting them as "your own life", which D-019 forbids, so the block is rewritten to say these are authored background and the seeded episodes carry that label in memory. The model can speak in its ordinary character voice, while a sincere question about being human, having a body, or having lived an event must receive an honest answer. Do not force a canned sentence on every turn. These are proposed storage and prompt rules to meet D-004, D-018 and D-019.

The current immutable core has no AI-status statement (`backend/app/persona/profile.py:136-142`), and the mandatory prompt rules do not supply one (`backend/app/cognitive/identity.py:784-790`). The existing output filter is also in tension with that design. `_validate_partial_response` rejects four phrases, “as an ai”, “i am an ai”, “how can i help you” and “as a language model”, at `backend/app/cognitive/action.py:718-731`. Preserve the intent to block stock assistant disclaimers, but scope the block so it does not reject a truthful in-character answer on a sincere identity probe. ## 5. Memory: supersession before new retrieval machinery

D-023 sets the first memory change: wire the existing `TemporalMemoryStore` and filter superseded facts at read. There are two partial mechanisms (rows 7a and 7b). The memory rows already carry `contradicts_id` and `valid_until` (`backend/app/state/memory_store.py:1518-1527, 1660-1667, 1677-1695`) and nothing filters on them. `TemporalMemoryStore` is constructed and injected (`backend/app/cognitive/core.py:98-100, 187-190`) but has no writer and no reader, so there is nothing to filter yet. Wiring it therefore has two steps: a belief writer that extracts subject, predicate and object from turns, which is language work with its own eval (extraction precision and recall on lifesim assertions), then the read filter. Phase 04 picks one store for validity; the default is `TemporalMemoryStore`, per D-023, with the columns on memory rows kept only as evidence. Architecture Invariant 9 applies: contradictions preserve evidence and history (`ARCHITECTURE.md` section 32). Not a fresh graph or PageRank subsystem.

At read time, retrieval must exclude records whose validity ended or whose successor supersedes them, while preserving provenance and access to prior values for explicitly historical questions. A correction does not erase history: “What is the current address?” should return the latest supported fact; “What address did I give you last year?” may return a superseded record with its date and status. Contradictions without a confirmed successor remain uncertain and should not silently invalidate both records. This is the proposed read contract; exact policy for unresolved contradictions belongs in the slice design.

Compare three arms on fixed histories and queries: a temporal-filtering arm; a full-history prompt with persona and no retrieval advantage; and the applicable V3 baseline. The full-history arm tests whether explicit supersession adds value beyond presenting all episodes. Score stale present-tense answers, correct historical answers, abstention when evidence conflicts, and whether changing one episode changes the predicted answer. Also check that rest-phase replay keeps superseded rows, since decay can delete them (row 12). Use M-5 and NF-6 scenarios from the V3 foundation; do not reuse a percentage unless its source and denominator are verified. D-021 still gates acceptance on beating both V3 and the bare model with persona and full history.

## 7. Model seam and state contract

D-035 makes the external ledger authoritative, with an optional in-model cache in a future model. The provider-neutral client protocol exposes generation, image description, health and close methods (`backend/app/llm/__init__.py:20-50`), with provider construction in the same module (`:53-87`). `ModelRole` and role requirements exist (`backend/app/llm/model_roles.py:55-68, 152-168`), and the cognitive core constructs a negotiator (`backend/app/cognitive/core.py:24, 116`), but calls are not routed through the role contract (`research/phase01-compare/T5.md`, sections 3 and 4). Proposed contract:

1. **Capability descriptor.** Each backend reports supported roles, structured-output capability, streaming, vision, context limits, sampler controls and any state-channel support. Capability checks happen at mind creation and invocation; a missing capability returns an explicit unsupported result, not silent fallback.
2. **Structured state channels.** Keep authoritative state outside the model. Pass declared channels such as identity, current affect, drives, retrieved memories, uncertainty and action intent as typed fields with source and version. The adapter may render these fields into a prompt for a text-only model. It must not turn a channel into an unsupported factual claim.
3. **ModelRole on every LLM call.** Route generation, ToM, reflection, memory compression, vision description and any judge call through a named role. The role is part of trace and intervention records, not an untracked string at a call site.
4. **Embedding provenance per row.** Store embedding model id and dimension with each vector row. Validate dimensions and model identity at write/read boundaries. An embedding model change cannot silently reinterpret old vectors.
5. **Single home for model-specific behavior.** Keep prompt directives, role mapping, parsing, structured-output adaptation, sampling translation and backend capability negotiation in the adapter package. The cognitive state schema and intervention API stay model-neutral. Behavioral equivalence across model tiers is not assumed; conformance is measured per pinned model (item 7).
6. **Future from-scratch hook.** A future model can add an internal cache of externally authoritative state, keyed by ledger revision and provenance. The cache is discardable and rebuildable. Read/write, clamp, replay, backup and restore still operate on the external ledger, so the cache cannot become a second authority (D-035). D-034 sets a narrow 124M–200M random-weights role model behind a 30M–60M controllability pilot; no rented compute before pilot gains, frontier-generated training data waits for provider terms to be checked (R-14), and state-trace logs wait until NF-12 (mood fed its own prior value) and NF-23 (hostile text raising integrity) are fixed, so the traces are not poisoned (D-034). The pilot and from-scratch training are a separate research track (D-033, D-034, D-013). The early size sweep, 135M–7B on a narrow persona role, is a slice in section 12 and waits for the GPU (D-035, D-013, D-036).
7. **Conformance measure and seam intervention.** Two parts, kept apart. *Adapter check (deterministic):* a stub backend that returns malformed or empty structured output must produce an explicit failure result, never a silent fallback. If the stub passes silently, the adapter has failed, which is the "no" this check can return. *Channel-fidelity probe (language work, human-calibrated):* per pinned model and role, change one supplied channel value (trust low versus high, one memory present versus absent, AI status present versus absent) on a frozen probe set and count replies that contradict the supplied value. AI status and memory presence can be checked by string and id match; contradiction of trust or affect needs a judge, which is a screening tool until calibrated on a human-rated sample (section 8). Also record the schema-validation failure rate, and run the same probes on the unadapted prompt as a control. A model fails conformance when channel fidelity falls below an absolute floor fixed before the run. Its run-to-run variation on identical input is reported beside the floor and is not used to set it.

D-026 and D-029 constrain this seam: select and pin the model once per mind, with a checkable artifact identity; restore only against the same model. The acceptance comparison can run different minds on different tiers, but never swaps the model underneath a live mind. D-024 requires one architecture and a result table for local 4B–9B and frontier-through-local-Claude-Code test tiers. The frontier row is a test ceiling, not a deployable home for a long-lived mind (D-032). Any GPU work still requires Aniket's go-ahead (D-013).

### Intervention battery

Freeze scenarios, seeds, outcomes and smallest effect of interest before running. Use offline test copies permitted by D-029 and delete them after each run. For each intervention, hold user inputs and history fixed unless the manipulation explicitly changes one of them.

| Intervention | Operation | What it separates |
|---|---|---|
| Clamp | Set one stored row to a fixed value for the run; keep other rows and context unchanged. | Whether the row changes its named behavior channel. |
| Swap / transplant | Replace one row's trajectory with the same row from a matched offline copy. | Whether a specific history, rather than only the current level, matters. Never swap the model of a live mind. |
| Shuffle | Permute the row's history within a matched session or across matched sessions while preserving the marginal values. | Whether order and correspondence to user events matter. |
| Open-loop replay | Replay a recorded state trajectory while changing user input, or replay the same inputs with the state trajectory fixed. | Whether state responds to the environment and later behavior, rather than acting as a scripted overlay. |
| Placebo directive | Inject a well-formed but unrelated state directive; compare with true state channel and no directive. | Whether an LLM follows prompt form alone, independent of stored state. |
| Layer lesion | Disable one layer's writes/reads while leaving the other paths intact. | Whether the D-031 double dissociation appears. |
| Directive hidden | Remove only the verbal state directive while preserving other state channels. | Whether a state-to-words result is prompt echo. The current code has additional state paths through emotion label, sampler options, global controls and retrieval, so record each channel (`backend/app/cognitive/action.py:883-886, 940-970`; `pipeline.py:677-679`). |

The fixed D-031 layer predictions are the preregistered tests: reactive lesion degrades timing and barge-in, not memory truth; deliberative lesion degrades planning and decision quality; reflective lesion degrades cross-session identity and consolidation, not within-turn timing. No double dissociation means report null N5 and treat the layer labels as descriptive paths.

### Null types and reporting

Pre-register and report all six types, including when they do not favor the architecture (`research/phase01-claude/T4-measure.md:186-194`):

1. **N1, equivalence:** full architecture and bare model with full history fall within the equivalence margin on all primary outcomes at a tier. Report no added benefit beyond full history at that tier.
2. **N2, compensation:** architecture helps the small local tier but is equivalent to the bare arm at the frontier test tier. Report that architecture may substitute for model capacity; show both rows.
3. **N3, decorative state:** state intervention effects fall below the pre-registered smallest effect, or open-loop replay matches the live loop. Report that the tested state persisted but did not show causal reach.
4. **N4, proxy gaming:** automatic or model-judge gains do not reproduce in blinded human ratings. Human ratings remain primary for claims about perceived coherence.
5. **N5, frame failure:** the three layer lesions fail the pre-registered double dissociation. Keep the path names but withdraw a claim of distinct layer function.
6. **N6, horizon flip:** a short-horizon gain reverses at the long horizon. Report both horizons without selecting the favorable window.

Consequences (`research/phase01-claude/T4-measure.md:187-196`): if N1, N2 or N3 occurs for a mechanism, that mechanism leaves V4 or is renamed; N4 means claims rest on blinded human ratings only; N5 keeps the layer names as path labels; N6 means both horizons are reported and no horizon is chosen.

Failure to reject a null hypothesis is not proof of no effect. Use equivalence bounds for N1 and report intervals for all outcomes. LLM judges are screening tools until calibrated against human judgments. A Turing-style pass is never a gate because it conflicts with disclosure (D-004).
